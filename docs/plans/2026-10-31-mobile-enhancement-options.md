# 移动端增强三选一：调研对比

日期：2026-10-31 ｜ 状态：待拍板 ｜ 范围：`v1.1.0-an`（Expo 51 / RN 0.74.5 / Android APK）

## 1. 背景

收尾计划（`2026-10-25-acceptance-audit-closure-plan.md`）第六批要求：收尾完成后从「本地通知 / 到期提醒」「桌面小组件」「滑动手势」中三选一启动。本文只做方案对比与验收草案，选定后另开实现批次。

## 2. 现状与约束

- Expo 51 + React Native 0.74.5 + TypeScript；AsyncStorage 适配 `IStorage`；HTTP 云同步与 Web 同构。
- 工程自包含（`shared/` 为 `packages/*` 内嵌副本，改逻辑先 `npm run sync-shared`）；APK 通过本地 gradle `assembleRelease` 或 EAS preview 交付。
- 当前只交付 Android APK，未交付 iOS；小组件的 iOS WidgetKit 方案暂不适用。
- 现有列表交互：长按 300ms 激活拖拽排序；新增手势必须与它仲裁，不能互相抢事件。
- 现有待办字段已有 `remindAt` / `remindLeadMs` / 循环 `nextDueDate`，通知方案可直接复用，不需要改数据模型。

## 3. 对比总表

| 选项 | 用户价值 | 实现成本 | 平台/依赖 | 主要风险 | 建议 |
|---|---|---|---|---|---|
| 本地通知 / 到期提醒 | **高**：手机离开应用也能收到提醒，和桌面纸片提醒对齐 | 中：`expo-notifications` + 权限 + 调度/重排 + APK 重打 | Android 13 通知权限；Android 12+ 精确闹钟权限；应用被杀依赖系统调度 | 精确时间受系统省电/权限限制；编辑待办后必须重排；Expo Go 不能作为最终验证环境 | **优先做** |
| 桌面小组件 | 中：主屏一眼看今日待办 | 高：Android App Widget 原生 Kotlin + config plugin/prebuild + 数据桥接 | 需要 dev build / prebuild；iOS 另需 WidgetKit（当前不交付） | 原生代码与机型适配成本高；RN 与原生数据同步易出错；测试周期长 | 最后做 |
| 滑动手势 | 中：左滑完成/删除/稍后，操作更快 | 低–中：`react-native-gesture-handler` + reanimated（或 PanResponder） | Expo SDK 51 兼容；Android 真机验证 | 与长按拖拽排序冲突，需要手势仲裁；误删需要确认/撤销 | 第二做 |

## 4. 逐项分析

### 4.1 本地通知 / 到期提醒（推荐优先）

**做法**
1. 安装 `expo-notifications`（用 `npx expo install` 解析 SDK 51 对应版本），配置通知渠道、图标与颜色。
2. Android 13+ 请求 `POST_NOTIFICATIONS`；需要精确到点时处理 `SCHEDULE_EXACT_ALARM`（Android 12+），拿不到权限时降级为系统允许的近似时间。
3. 应用启动 / 回到前台 / 待办新增或编辑 / 同步合并后，重排未来提醒：单次任务用 `remindAt`；循环任务用 `nextDueDate - remindLeadMs` 计算下一次；完成/删除时取消对应通知。
4. 通知点击打开应用并定位到待办详情；通知动作可先只做「打开」，完成/稍后作为二期。
5. 测试：前台、后台、应用被杀、重启手机、改时间/改提前量、循环推进、权限拒绝。

**验收草案**
- 创建 2 分钟后到点的待办 → 应用退到后台/杀掉 → 仍按时收到通知（允许系统近似时说明误差）。
- 编辑提醒时间后旧通知不响、新时间响；完成/删除后不再响。
- 循环任务完成后下一次提醒按新 `nextDueDate` 排。
- 拒绝通知权限时有可读提示，打字建待办路径不受影响。

**成本**：约 1–2 天（含 APK 重打与真机测试）；无需原生 Kotlin。

### 4.2 桌面小组件（成本最高）

**做法**
1. Android App Widget（Kotlin/Java + `AppWidgetProvider` + RemoteViews），用 Expo config plugin 或 prebuild 接入原生工程。
2. RN 侧在待办变更/同步合并后写入 SharedPreferences（或通过原生模块传递），小组件读取并刷新；需要处理进程被杀后的数据一致性。
3. 小组件只做只读摘要（今日待办数 + 前 3 条），点击打开应用；编辑/完成仍在应用内。
4. iOS 若要支持，需 WidgetKit + App Group，当前无 iOS 交付，暂不做。

**验收草案**
- 主屏添加小组件 → 显示今日待办数与标题；应用内增删改后小组件在可接受延迟内刷新。
- 应用被杀/重启后数据仍正确；不同桌面启动器/图标密度下布局不溢出。

**成本**：约 3–5 天起（原生代码 + prebuild + 多机型测试）；风险最高，不建议作为第一项。

### 4.3 滑动手势（成本最低）

**做法**
1. 安装 `react-native-gesture-handler` + `react-native-reanimated`（SDK 51 对应版本），或先用 PanResponder 做 MVP。
2. 左滑露出「完成 / 稍后 / 删除」；删除必须二次确认或提供撤销；右滑可留空或做「完成」。
3. 手势仲裁：横向滑动超过阈值才激活，长按 300ms 仍走拖拽排序；滑动中禁止触发点击。
4. 测试：与长按拖拽、列表滚动、点击详情的冲突；快速连滑；删除确认/撤销。

**验收草案**
- 左滑出现动作且不误触详情；长按仍能拖拽排序；列表纵向滚动不被横向手势打断。
- 删除有确认/撤销；完成后列表与同步状态正确。

**成本**：约 1 天（MVP + 真机调手势冲突）；无需原生 Kotlin。

## 5. 推荐顺序与决策点

1. **本地通知 / 到期提醒**：价值最高、与桌面提醒对齐、无需原生代码；建议先做。
2. **滑动手势**：成本最低、体验提升直接；在通知之后做。
3. **桌面小组件**：原生成本与机型风险最高，放最后；若没有强需求可不做。

**需要拍板**
- 选哪一项作为下一批次（建议 A 本地通知）。
- 是否接受重打 APK / 使用 dev build 做真机验证。
- 通知的精确闹钟权限拿不到时，是否接受系统近似时间（建议接受并提示）。
- 滑动手势若选，删除是「二次确认」还是「撤销条」（建议二次确认，和桌面删除语义一致）。

## 6. 不在本调研范围

- iOS 交付与 WidgetKit。
- 远程推送（服务端发通知）；本方案只做本地到期提醒。
- 通知内的完成/稍后动作（可作为通知方案二期）。
- 移动端 UI 大改版；三项增强都不改现有 Swiss 视觉与数据模型。
